# Электронная очередь в сервисном центре

REST-сервис электронной очереди. Клиент берёт талон на одну из услуг, оператор вызывает следующий талон, завершает обслуживание или отменяет талон.
Завершить можно только SERVING, отменить — только WAITING. Одновременно в статусе SERVING по каждой услуге не больше одного талона.

## Стек

- Java 17+, Spring Boot 3.5 (Web, Data JPA, Validation)
- PostgreSQL 17 (запускается через Docker Compose)
- Liquibase (миграции в YAML)
- Lombok
- springdoc-openapi (Swagger UI)
- JUnit 5, Mockito, MockMvc

## Запуск

Необходимы JDK 17+, Docker с Docker Compose.

1. Создайте файл с настройками базы (значения по умолчанию подходят без изменений):

   ```bash
   cp .env.example .env        # Windows (cmd): copy .env.example .env
   ```

2. Запустите PostgreSQL:

   ```bash
   docker compose up -d
   ```

   База доступна на `localhost:5433` (порт хоста 5433, внутри контейнера 5432), имя базы `ticketDb`, пользователь и пароль `postgres`.

3. Запустите приложение:

   ```bash
   ./mvnw spring-boot:run      # Windows: mvnw.cmd spring-boot:run
   ```

   Миграции Liquibase применятся автоматически при старте. Сервис слушает порт 8080, все адреса начинаются с `/api`.

4. Swagger UI: <http://localhost:8080/api/swagger-ui.html> (описание API в JSON: <http://localhost:8080/api/v3/api-docs>).

## Тесты

```bash
./mvnw test
```

Тесты не требуют запущенной базы данных:

- TicketServiceImplTest — unit-тесты сервисного слоя (JUnit 5 + Mockito), в том числе вызов следующего талона;
- TicketControllerTest — интеграционные тесты контроллера на `@WebMvcTest` (валидация, HTTP-коды, формат ошибок).

## API

Базовый адрес: `http://localhost:8080/api`

| Метод   | Адрес                       | Описание                                                      | Успех |
|---------|-----------------------------|---------------------------------------------------------------|-------|
| `POST`  | `/tickets`                  | взять талон                                                   | 201   |
| `GET`   | `/tickets/{id}`             | получить талон по id                                          | 200   |
| `GET`   | `/tickets`                  | список талонов, фильтры `status` и `service`, сортировка по `createdAt` по возрастанию | 200 |
| `PATCH` | `/tickets/next`             | вызвать следующий талон, необязательный параметр `service`    | 200   |
| `PATCH` | `/tickets/{id}/done`        | завершить обслуживание (только из `SERVING`)                  | 200   |
| `PATCH` | `/tickets/{id}/cancel`      | отменить талон (только из `WAITING`)                          | 200   |

### Примеры запросов

Взять талон:

```bash
curl -X POST http://localhost:8080/api/tickets \
  -H "Content-Type: application/json" \
  -d '{"clientName": "Иван Петров", "service": "PAYMENTS"}'
```

Ответ `201 Created`:

```json
{
  "id": 1,
  "number": 1,
  "clientName": "Иван Петров",
  "service": "PAYMENTS",
  "status": "WAITING",
  "createdAt": "2026-10-19T12:00:00.123456",
  "calledAt": null
}
```

Получить талон по id:

```bash
curl http://localhost:8080/api/tickets/1
```

Список талонов с фильтрами (оба параметра необязательны):

```bash
curl "http://localhost:8080/api/tickets?status=WAITING&service=PAYMENTS"
```

Вызвать следующий талон по услуге:

```bash
curl -X PATCH "http://localhost:8080/api/tickets/next?service=PAYMENTS"
```

Завершить обслуживание и отменить талон:

```bash
curl -X PATCH http://localhost:8080/api/tickets/1/done
curl -X PATCH http://localhost:8080/api/tickets/2/cancel
```

### Формат ошибок

Все ошибки возвращаются в едином JSON-формате.

Для ошибок валидации поле `details` содержит список сообщений по полям.

| Код | Описание                                                                                                                                        |
|-----|-------------------------------------------------------------------------------------------------------------------------------------------------|
| 400 | невалидное тело запроса (пустое или слишком длинное `clientName`, не указан `service`), некорректный JSON, неверное значение параметра или enum |
| 404 | талон с таким `id` не найден; нет талонов, которые можно вызвать через `/next`                                                                  |
| 409 | `done` не для `SERVING`; `cancel` не для `WAITING`; по услуге уже есть `SERVING`; конфликт при параллельных запросах                            |
| 500 | непредвиденная ошибка                                                                                                                           |

Пример ошибки валидации:

```bash
curl -X POST http://localhost:8080/api/tickets \
  -H "Content-Type: application/json" \
  -d '{"clientName": "", "service": "PAYMENTS"}'
```

```json
{
  "status": 400,
  "message": "Ошибка валидации",
  "details": ["Имя не должно быть пустым"]
}
```

## Проектные решения

### Как выбирается «следующий» талон

Следующим считается самый старый талон в статусе `WAITING` (сортировка по `createdAt`, затем по `id`).

- **`PATCH /tickets/next?service=X`**
  - если по услуге `X` уже есть талон в статусе `SERVING`, возвращается `409`;
  - если талонов `WAITING` по услуге нет, возвращается `404`.
- **`PATCH /tickets/next` без параметра.** В задании этот случай не детализирован, поэтому поведение следующее: берётся самый старый `WAITING` среди услуг, по которым **сейчас нет `SERVING`**. Иначе самый старый талон занятой услуги блокировал бы вызов талонов всех остальных услуг. Если подходящих талонов нет, возвращается `404`. Выборка выполняется одним запросом с подзапросом `NOT EXISTS`.

Пока оператор не вызовет `done` для текущего талона, следующий талон той же услуги вызвать нельзя.

### Правило «не больше одного SERVING на услугу»

Правило проверяется в сервисном слое и дополнительно защищено на уровне БД частичным уникальным индексом PostgreSQL:

```sql
CREATE UNIQUE INDEX uq_ticket_one_serving_per_service
    ON ticket (service) WHERE status = 'SERVING';
```

Если два оператора одновременно вызовут талоны одной услуги, проверка в Java может пройти у обоих, но второй `UPDATE` нарушит индекс. Исключение `DataIntegrityViolationException` обрабатывается и превращается в `409 Conflict`, запрос можно повторить.

### Нумерация талонов

Номер выдаётся сервером как `max(number) + 1`. Колонка `number` имеет ограничение `UNIQUE`: таким образом при одновременном создании двух талонов дубль номера невозможен, а второй запрос получит `409` и может быть повторён.
